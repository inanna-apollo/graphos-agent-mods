### Shapes the code relies on

- `tool.call` `e` keys: `operation`, `variables`, `tool`, `tool_use_id`. `variables` is `{} | string`.
- `$.mcp.call` returns `{ content: [{ type: "text", text: "<json>" }], isError }`. The JSON text holds the payload.
- `validate`: `{ bundleDigest, requestId, scope, valid, errors?: string[] }`. When invalid, `errors` holds compiler text that quotes the operation (untrusted), and one string can contain several `Error:` blocks.
- `bundleDigest` changes mid-session (seen `e5f6…` → `a1b2…` within hours), so the cache must key on it.
- `introspect`: `{ bundleDigest, requestId, scope, types: string[] }` (SDL strings).
- `dry_run`: `{ bundleDigest, results: [{ denyOperation, fields: [{ decision, path }] }] }`. `path` is a dotted response path built from **response keys, so aliases are used** (`hits: confluence_search { items: results { heading: title } }` → `hits.items.heading`). The IR builds each field's path from `alias ?? name` and maps it to the schema coordinate. The real name is always what gets shown.
- Agent Services errors carry `extensions.code`. `UPSTREAM_AUTH_REQUIRED` includes `sources[].authorizationUrl`, which the pane should show as its own state.

## Permission checks on a plugin's own calls

- A hook's `$.mcp.call` is permission-checked like a model tool call unless a person's command or press is behind it, and its dialog queues behind any pending one.
- Enrichment therefore runs from a `$.clock.every` pump started in `session.start` (the documented home for "work that outlives one event"), not from inside `tool.call`.

## Engine facts learned building the pane (Oct 6 2026, 2.1.290–2.1.292)

Each was verified with a probe or live in the tester; the code depends on them.

- **Hover cards.** An absolute Box over the pointer counts as on its parent, so a layer spanning rows kills every hover under it. The engine clips an absolute Box to a zero-height absolute parent. So every card is a direct child of the pane root, placed with `top` below its trigger or `bottom` above it. `bottom={0}` on a root child lands on the last content row, because the root's height is its content's. Later siblings paint over an earlier absolute Box, so cards come last.
- **Sticky hovers.** A revealed hover Box joins its group, so it stays lit while the pointer rests on it. A card that spans the next row's trigger holds the old card up, so row tips live inside their own row.
- **Fragments** drop nested arrays. Use a Box.
- **Buttons** take no color, and a plain Button draws its hotkey in the accent color.
- **Markdown links** draw in ANSI 94, which is gray in some themes. Inline code inside a link draws in 256-color 153, a fixed light blue. With `onLinkPress` and `pressableLinks`, a plain click presses the link.
- **`$.ui.notice`** is accepted but not drawn for MCP tool dialogs, so the verdict line decorates the call's `ToolUse` / `ToolGroup` row instead.
- **Reads.** A dispatch's `$` reads one moment. A pump started on a `tool.call`'s `$` never sees later writes while that dialog is up, so the pump runs on the session's `$`.
- **The harness pointer** reaches only `Client` elements, and tmux-sent mouse events don't hover, so hover is checked by hand.
- **`tool.check`.** A `tool.check` hook can lift the engine's `ask` to `allow`; this mod does so only for a call that fits the person's trust rules, never past a deny or an organization `ceiling`. A `tool.check` hook's `e.input` is `{ operation, variables }`, and `e.tool_use_id` is set on the model's own calls.

## Engine facts for the standing line, attribution, spinner, file watch and transcript RESULT (Oct 6 2026, 2.1.292)

From the reference docs (`.claude-plugin/types/claude-code/index.d.ts`) unless marked *live*. Seen live in the tester (Oct 7 2026): the standing line, the learned-site line, the transcript RESULT block, `/gas setup` and its prompt-box draft, the receipts line and `/gas links`. Not yet seen live: the spinner text, a subagent's label, and the notices on saving trust.graphql or links.toml. Each entry says what is still to check.

- **Standing line: `$.ui.status`, not `SessionMode`.** `$.ui.status(text)` pins one line per plugin under the prompt until the next call replaces it (`undefined` clears it; 2000 characters drawn). `SessionMode` is the footer's list of dim mode labels (`focus`, `memory paused`) joined by ` & `: a mode, not a counter. A dispatch's `$` reads one moment, so the line is computed from what `update` resolved (it returns the value it wrote), never from a read-back. *Seen live (Oct 7), under the prompt in the terminal. Still to check:* the desktop, and that `/clear` leaves nothing stale.
- **Subagent attribution.** `tool.call`'s `e.agentId` is set when a subagent's or teammate's loop makes the call and absent on the main loop; `tool.check`'s carries the same id. `$.agent.list()` names each agent's `type` and `description` (the Agent call's few words), but not an agent a workflow started or an engine fork, whose ids no list names: the pane then says `from subagent` alone. The label (`type: description`) is looked up beside the dialog, bounded to 5 s, and patched onto the call; nothing waits on it. A teammate's type is `teammate`, so its line reads `from subagent · teammate: …`. The test harness passes `agentId` through `$.tool.call({ …, agentId } as never)` to the plugin's hook, which is how tests/agent.test.ts makes a subagent's call. *Not yet seen live; check:* a real Explore agent's Agent Services call shows its type and task.
- **Spinner.** `Spinner` props are `word`, `message` (a state's override, else null), `suffix` (the ellipsis) and `mode`; none names a tool or a call, and the instance's `requestId` is the agent id. `mode: 'tool-use'` spans the whole tool phase (the engine sets it when the assistant message ends), so a permission dialog and the execution it leads to are one mode. The reference docs say nothing about the spinner while a dialog is up, so the hook claims it only for a call whose permission check answered allow (the engine's own rule, or our trust-rule lift), where no permission dialog can be: the check hook starts the text, the headline's arrival updates it, and the call's end (or an abort, an orphan's settle, session.end) clears it. The text is one small atom, so a spinner row subscribes to it and to no call's state; the hook is matched on `mode: 'tool-use'` so other modes cost nothing, and leaves a spinner whose `message` is already set alone. *Not yet seen live; check:* whether the spinner is drawn at all while a dialog is up; if it is not, calls that ask could be named too once they run (drop the allow condition in the check hook), and the headline's arrival redraws the row.
- **Watching the config files.** A `classic.SessionStart` answer's `watchPaths` takes absolute paths, which need not be in the project, and the engine raises `classic.FileChanged` `{ file_path, event: 'change' | 'add' | 'unlink' }` for them; `file_path` arrives as the path was given, and a `FileChanged` matcher narrows on it. A settings hook of the person's own that answers with its own `watchPaths` can replace the list until the next session. A save is only reported for `trust.graphql` (see .claude/CLAUDE.md); `links.toml` is read again, after a 300 ms settle that folds an editor's unlink-and-add into one reload, and one transcript line says how many row rules and how many were skipped, and which hosts a click may now open that it could not before (a save is what can widen that). *Not yet seen live; check:* a save of either file in the tester raises FileChanged once.
- **RESULT in the transcript.** A standalone call's result is its own `ToolResult` event (props `tool_use_id`, `tool`, `output`, `isErrored`); `ToolUse.output` and a `ToolGroup` call's `output` carry the same record, and an *expanded* group draws it inline inside each `ToolUse` row. Nothing on `ToolUse` says whether its row is standalone or inside an expanded group, so a block added there would double on standalone rows: expanded groups get none. A *folded* group draws one count line and no result, so the `ToolGroup` hook adds each call's block under its verdict line. The block goes ahead of the engine's own drawing (`next(e)` stays whole beneath it); the rows read a record by `tool_use_id`, written when the call settles and again when its analysis ends (a row with no record reads the calls state once and records it, which subscribes it to that state until its next draw). The record is memory only: after a reload the last 20 calls draw a block from the calls state and older rows draw none. Record keys press through the pane's own path (`Markdown` with `onLinkPress`, and `surfaceOpened` off the terminal). *The block was seen live (Oct 7); the rest of this list is not recorded as checked:* what the engine draws for an MCP `execute` result (the block's placement above it); that a click on a record key in the transcript raises `ui.press` (the pane's does); whether Agent Services `execute` rows fold into groups in practice (the spike saw one fold); and the block's look at narrow widths.

## Learned sites, /gas setup, the store and the manifests (Oct 6 2026, 2.1.292)

- *Live (Oct 7):* Agent Services reaches Jira through Atlassian's API gateway, so every `self` in a Jira answer is `https://api.atlassian.com/ex/jira/<cloud id>/...`, which names no site. That includes `jira_getCurrentUser { self }`, the first setup question, which taught nothing. A status's and a priority's `iconUrl` stay on the site (`https://<name>.atlassian.net/images/icons/statuses/...`), so `iconUrl` is a URL key. The Atlassian setup question asks five issues for `fields: ["status", "priority"]`: on a clean install (Oct 7) one issue's status taught nothing, because a status Jira Software manages (In Review) has its icon on the gateway too, while every priority icon seen was on the site. `slack_authTest { url }` taught the Slack workspace.

From the reference docs, the test harness and `claude plugin validate` unless marked *live*. Seen live (Oct 7): the learned-site line (Slack, then Atlassian), `/gas setup` with its prompt-box draft, and `/gas links`. Each entry says what is still to check.

- **Learned sites.** A site is taken from an Agent Services response in `tool.call`, before `outcomeOf` runs (record URLs are worked out inside it), and from the saved copy of an oversized result. The gate is cheap: nothing is parsed unless the Atlassian site or Slack workspace is still unset (`baseSources` from `loadLinkConfig`). A learned site is kept in `$.store` under `learnedSites` and checked with `tenantOf` on every load. A drawn row works its links out from the current link config, so a site learned a moment later still reaches rows already drawn; learning first is what keeps the stored preview URLs right. `/gas setup` drafts two read-only queries, one for each unset site: `slack_authTest { url }` and five issues from `jira_searchAndReconsileIssuesUsingJql` with `fields: ["status", "priority"]`. *Live (Oct 7):* both answered on a real Agent Services and each taught its site (Slack's from `url`, Atlassian's from a status's `iconUrl`), the learned-site line once for Slack and then once for Atlassian.
- **`$.store`.** A JSON file of the plugin's own, `get` of an unset key is `undefined`, `set` rejects past 4 MiB. Keyed by plugin name; a renamed plugin starts it empty (so the snapshots and timing flags start off). The harness takes `store.get`, `store.set` and `store.delete` hooks like any event, answering `{ value }`. *Check live:* that a learned site is still there in the next session.
- **`$.session.version()`** answers `{ version, base?, builtAt? }`; a development build's `base` ends in `-dev`, which `isOlder` cannot compare (it takes dotted releases only), so `/gas setup` says so rather than guess. A throw is read as an unknown version, and nothing is logged. *Check live:* the session-start line on a release older than 2.1.290, if one is at hand.
- **`$.prompt.fill` from a command.** `/gas setup` fills the prompt box from a command's dispatch, as the access-request button does from a press. The hook answers `{ isFilled, refusal }` itself while `prompt.read` wraps `{ value }`, in the test harness. *Live (Oct 7):* the composer takes the draft right after `/gas setup`. *Not recorded:* that it appends after what was already typed.
- **Options are not checked against the manifest in tests.** `{ options: { snapshots: true } }` is accepted for a key `plugin.json` no longer declares, so a test can hide a missing declaration. The snapshot options were taken out of `userConfig` (a person never sets them); `/gas snapshots on` is the way, and unset is off at 50, 64 and 84 columns.
- **`claude plugin validate`.** It validates `.claude-plugin/marketplace.json` too. A marketplace's description sits under `metadata.description` (a bare one warns), `"source": "./"` and an owner name pass, and `displayName`, `homepage`, `repository` (a string), `license` and `keywords` in `plugin.json` raise no warning. `--strict` passes with the repo's own guide at `.claude/CLAUDE.md`, where Claude Code loads it as project memory; at the plugin root it was the one warning, because a `CLAUDE.md` there is not loaded.
- **Installing from GitHub.** *Live (Oct 7):* `claude plugin marketplace add inanna-apollo/graphos-agent-mods` and `claude plugin install graphos-agent-mods@graphos-experiments` in a fresh profile clone the repository over SSH, or over HTTPS where SSH fails. `plugin.json` has no `version`, so the plugin is versioned by commit and an update reaches people who already installed; no lockfile is tracked, because a `package.json` with a lockfile at the root makes the install run npm.
- **Hover tests are close to the harness's 5 s limit.** The slowest (`GnarlyOverview`, `trusted`, `asked`) take 3 to 7 s and can time out on a busy machine; run the suite again before suspecting a change.

## What the context receipts assume (Oct 6 2026)

The receipts line was seen live in the tester (Oct 7 2026); each entry says what is still to check. The receipts (src/weight.ts, src/view/receipt.ts) read only what the mod already read: the result's text, and for an oversized result the file Claude Code saved.

- **Units.** Claude Code's own stand-in says `Output too large (58.2KB)` and `src/result.ts` has always read a KB as 1,024 bytes; the receipts say KB the same way. *Check:* a result whose stand-in says N KB reads as about N KB in the pane.
- **What Claude saw of an oversized result.** `<persisted-output>` carries `Preview (first 2KB)` and the saved path; the older `exceeds maximum allowed tokens` text carries the path and no preview. The receipts say "a short preview and its path" for both. *Check:* what Claude is actually shown for each form; the older one is the less exact claim.
- **Compact bytes.** The weight is the response as `JSON.stringify` writes it, not the text as Agent Services sent it, so a service that pretty-prints cost the context a little more than the pane says. *Check:* whether Agent Services' `execute` text is compact (`curl`-style single line) or indented; if indented, the measure undercounts by the indentation.
- **The saved file.** A saved tool result is content blocks pretty-printed, the response text inside as a string; `responseOf` unwraps it once, so the weight is the inner response's. `$.fs.read` of it is bounded by `MAX_SAVED` (2,000,000 characters); a larger file is not read back, and the outcome stays `isTooLarge` with Claude Code's own figure.
- **Reading is counted once.** The standing line's bytes are added when a call's outcome is recorded (`countRead` in the `tool.call` hook), once per call; a call whose outcome was read back from a saved file is not added (Claude read a preview, not that). `$.state` keeps the total as `tally.bytes`, absent in state an older build wrote (counted as none).
- **Cost.** The walk is one pass over the parsed response after `JSON.parse`: in Node, a 1.2 MB response of 78,000 values took 17 ms (its `JSON.parse` 3 ms), so a response at the 2 MB read-back bound is a few tens of ms. It runs in the `tool.call` hook after `next(e)` returns, before the row draws. *Check:* a large live result does not visibly stall the call's row.

## What the write preview assumes (Oct 7 2026)

The write preview runs no Agent Services call of its own. The argument and return shapes are the Agent Services schema as read on Oct 7 2026, and the rest is from the vendors' API documentation. Each entry says what to check in the tester, with a read-only query or by reading a write's own dialog (approve no write to check this).

- **Argument shapes.** Jira's `fields`, `update` and `transition` are opaque JSON; a model may pass them as objects in `variables` or as JSON strings, and both are read. Slack's `blocks` and `attachments` are strings, URL-encoded JSON in Agent Services' description; plain JSON is read too. *Check:* a real write's dialog shows the shapes the fixtures use.
- **What a response carries back.** Jira answers a transition, an edit (unless `returnIssue`), an assignment and a delete with no content, so RESULT confirms nothing for them; Confluence's page update returns the page (`title`, `status`, `version.number` when selected); Slack's post returns `ts` and `message.text`. *Check:* what `execute` returns for each, on a write someone else made on purpose, or in a sandbox, never by running one to test.
- **What a delete leaves.** Jira has no trash for issues or comments, Slack none for messages, and Confluence comments are deleted for good; a Confluence page or blog post deleted through the v2 API goes to its space's trash. This is from the vendors' API documentation, not observed. *Check:* the flag and the note against the vendor docs when the Agent Services bundle changes.
- **Broadcasts.** Only `<!channel>`, `<!here>` and `<!everyone>` (and a rich-text `broadcast` element) are flagged; a literal `@channel` typed as text is not, since Slack's post API does not link names unless asked. *Check:* whether Agent Services' `slack_sendMessage` sets `link_names`.

## A plugin's own `execute` call (Oct 7 2026, 2.1.292, *live*, read-only)

A throwaway probe plugin (never shipped) asked to run one fixed read, `query ProbeSelfRead { slack_authTest { url } }`, through `$.mcp.call(server, 'execute', …)` from a slash command, beside this mod in manual mode. It was declined at the dialog.

- **It raises its own dialog,** headed `Tool use · from the <plugin> plugin`, like any ungranted call. This matches spike 4.
- **This mod listed the call as an Agent Services call,** as if Claude had made it. A call's maker is now kept: `next.origin.plugin` in `tool.call` is `engine` for Claude's own calls and the plugin's name otherwise. The pane says `↳ from the <plugin> plugin`, with a card.
- **No `classic.PermissionRequest` line appeared** from the probe's hook before that dialog. Either the event did not fire for a plugin-made MCP call, or the `$.ui.log` from it was not drawn. *Check:* the same hook on a model-made Agent Services call's dialog.
